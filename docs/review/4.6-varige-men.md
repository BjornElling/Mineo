## Fund og rettelser

### 1. Engine var dead code — UI/PDF bypassede den kanoniske beregningsindgang (Høj, kontraktdrift)
**Lokation:** `MenberegningTab.tsx` (`beregningsResultat`-useMemo) vs. `varigemen-contract.md §1/§2` og `calculation-architecture.md §2`.

**Problem:** Kontrakt §1 udpeger `computeVarigeMenEngine` som "den kanoniske engine" og §2 regel 2 kræver at "beregning … kun [må] ske via det autoritative engine-modul". `calculation-architecture.md §2` fastslår tilsvarende at varige mén "kører bevidst et section-lokalt engine-flow … den kanoniske adgang [er] ét beregnings-entry … hvis resultat genbruges af PDF/debug uden genberegning". I praksis kaldte UI'en `beregnVarigeMenGodtgoerelseWithRates` **direkte**, og `computeVarigeMenEngine` var kun refereret af sin egen test — altså dead production code. Søsterdomænerne (renteberegning via `renteberegningEngine`, årsløn via `useAarsloenBeregning`) router korrekt gennem deres engine; varige mén var den eneste afviger.

**Risiko:** To parallelle indgange til samme beregning (dobbelt-sandhed); kontrakten beskrev en arkitektur koden ikke fulgte; fremtidig engine-niveau-logik (fx logging, guards) ville blive omgået.

**HANDLING:** ✅ **Rettet.** `MenberegningTab` router nu udelukkende gennem `computeVarigeMenEngine`. **Output-neutralt:** engine-laget er et rent gennemløb til `beregnVarigeMenGodtgoerelseWithRates` med identiske argumenter og uændret resultat — ingen beregningslogik rørt, tal byte-identiske. Ny ækvivalens-test (`varigeMenEngine.test.ts`) beviser tal-identitet engine vs. direkte kald på tværs af 5 inputkombinationer (alder/méngrad/sats/afrunding). PDF-stien genbruger fortsat det allerede beregnede `beregningsResultat` (genberegner ikke) — kontrakt §1/§4(4) opfyldt. Behøver ikke godkendelse: ingen synlig UI/UX- eller numerisk ændring.

### 2. Dokumentdrift i `docs/domain/varigemen/varige-men.md` (Lav)
**Problem:** Domænedokumentet var ude af sync med koden på tre punkter:
- `VarigeMenBeregningResult` manglede felterne `aldersreduktionBeloeb` og `beregningsaar` (begge findes i koden).
- Afhængighedstabellen listede `coerceToDanishDateString` og `parseDanishDate` som imports — begge er fjernet (koden gik tidligere ISO→dansk→Date, men den omvej blev bevidst afviklet; jf. kommentar i `varigeMenCalculations.ts`). `roundByMethod` og `calculateUtcAgeInWholeYears` manglede.
- Påstanden "`Math.ceil` er eneste afrundingsfunktion … der bruges hverken `roundByMethod` …" var direkte forkert: koden bruger netop `roundByMethod(value, 0, 'ceil')`.

**HANDLING:** ✅ **Rettet.** Resultattype, afrundingsafsnit, afhængighedstabel og "Indgangspunkter" opdateret til at afspejle koden (og at engine nu er den kanoniske indgang).

## Korrekthed / determinisme (verificeret, ingen fund)

- **Fail-closed på manglende sats:** `getRateForYear` bruger `hasOwnProperty` (ikke truthy-tjek), og engine/calc returnerer `null` ved manglende år samt ved sats `NaN`/`Infinity`/negativ. UI'ens beregningsdato er hårdt afgrænset til `varigeMenPrGradYearBounds` (2005–2026), så et år uden dækning ikke kan vælges. Dækket af eksisterende tests + de bekræftede null-cases.
- **Determinisme/locale/tidszone:** Alder beregnes via `calculateUtcAgeInWholeYears` (ren UTC-felt-sammenligning, ingen locale/TZ-afhængighed). Datoparsing via kanonisk `parseISODate`. Ingen `Date.now()`/`new Date()` i beregningsstien.
- **Floating-point/afrunding:** Slutbeløb afrundes via kanonisk `roundByMethod(..., 0, 'ceil')`. `aldersreduktionBeloeb` er bevidst udledt som `grundbeloebUdenReduktion − beregnetGodtgoerelse`, så de tre viste linjer (grundbeløb − reduktion = godtgørelse) altid afstemmer i både UI og PDF — værnet af eksisterende test.
- **Inputrobusthed:** `mengrad` afvises ved `undefined/0/<0/>100/NaN`; manglende fødselsdato/skadedato/beregningsdato → `null`. Ingen division, ingen array-operationer, ingen tom-liste-grene.
- **Aldersfradragsformel:** `beregnAldersfradragPct` matcher domænedoc-tabellen (basis 1%/år>39 cap 30; ekstra 1%/år>59 cap 10; total cap 40 ved 69+). Bredt grænsetestet (39/40/50/59/60/65/69/70/80). **Vurderet ikke** mod juridisk kilde (jf. AGENTS.md) — implementeret som angivet.

## Type-sikkerhed (verificeret)
- Ingen `any`, ingen usikre `as`/`!` i domænestien. `coerceToISODateString` (`ISODateString | null`) konverteres eksplicit med `?? undefined` ved engine-grænsen. Schema (`positiveWholePercentage` + `optionalIsoDateString`) er Zod-eneste-sandhedskilde; `VarigeMenValues` er afledt. `VARIGE_MEN_INITIAL_VALUES` er `satisfies PersistedSectionMap['varigemen']`.

## Konvergens med 4.0
Varige mén **delegerer ikke** til opreguleringsmotorerne. Satsen (`varigeMenPrGrad[beregningsår]`) slås op direkte pr. kalenderår uden opregulering — beløbet er allerede den årsregulerede lovsats. Korrekt og bevidst (jf. domænedoc); ingen tal-identitets-verifikation mod 4.0 relevant her.

## Sammenfatning

- **Vigtigste rettelse:** Den kanoniske `computeVarigeMenEngine` var dead code; UI/PDF kørte uden om den i strid med både `varigemen-contract` og `calculation-architecture`. UI router nu gennem engine (output-neutralt, tal-identisk), så varige mén konvergerer med søsterdomænernes engine-flow. Ny ækvivalens-test sikrer mod fremtidig drift.
- Domænedoc bragt i sync med koden (resultattype, afrunding via `roundByMethod`, korrekte afhængigheder).
- Beregningskernen er fail-closed, deterministisk, locale-/TZ-uafhængig og type-sikker; ingen beregningslogik ændret og intet afventer godkendelse.
- Punktet er **konvergeret med fundamentet** (4.0-relation afklaret: ingen opreguleringsmotor-delegering; engine-flow nu i tråd med kontrakten).
