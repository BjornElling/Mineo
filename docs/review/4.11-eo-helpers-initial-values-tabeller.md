## Fund og rettelser

### 1. (Lav) Døde, ikke-importerede barrel-filer — `helpers/index.ts` og `tables/index.ts`
**Lokation:** `src/domain/erstatningsopgoerelse/helpers/index.ts`, `src/domain/erstatningsopgoerelse/tables/index.ts`.
**Problem:** Begge `index.ts`-barreler re-eksporterer modulerne som namespaces (`export * as foo from './foo'`), men **ingen fil i hele kodebasen importerer dem** (verificeret: grep på `erstatningsopgoerelse/helpers'`, `.../tables'`, `helpers/index`, `tables/index` → 0 hits, inkl. tests og dynamiske strenge). `helpers/index.ts` var desuden **ufuldstændig**: den udelod bl.a. `eoSharedUtils`, `loenindkomstRowDerived`, `loenindkomstSatser`, `loenindkomstStateCleanup`, `midlertidigtEet*`, `offentligeYdelserRowInsertion`, `readableSummaryMessage`, `sygedagpengeInsertRows`, `sygeferiegodtgoerelse*`, `eoInputRelevance` — så barrelen gav et misvisende billede af modulets overflade.
**Risiko:** Ingen runtime-risiko (død kode). Vedligeholdelses-/konvergens-risiko: en ufuldstændig barrel inviterer til "halv import via barrel, halv direkte" og slører den kanoniske importflade. Alle faktiske callsites importerer allerede direkte fra de konkrete moduler.
**HANDLING:** ✅ Rettet — begge `index.ts` slettet. Typecheck + typecheck:test grønne efter sletning (intet brød). Direkte modul-imports er den etablerede og eneste faktiske importflade i området.

### 2. (Lav) Manglende type-binding på to initial-row-konstanter — drift-risiko
**Lokation:** `eoRowInitialValues.ts` (`initialOffentligYdelseRow`, `initialLoenudviklingManuelRow`).
**Problem:** `initialRow` (StandardLoen) var eksplicit typet som `Omit<StandardLoenTableRow, 'id'> & { id: '' }`, men de to øvrige initial-rækker var **utypede objektliteraler** (inferret struktur). Hvis et schema-felt blev tilføjet/omdøbt (fx i `offentligeYdelserRowSchema`), ville disse initial-rækker stille drive ud af sync uden en typefejl ved definitionen — og nye rækker ville blive oprettet uden det nye/omdøbte felt. Det er præcis den dobbelt-sandheds-/fail-open-risiko AGENTS.md §Type-autoritet og §Holdning (fail-closed) advarer mod.
**Risiko:** Ingen aktuel (felterne matcher schemaet i dag — bevist af typecheck). Latent: stille felt-drift ved fremtidig schema-ændring.
**HANDLING:** ✅ Rettet — begge konstanter er nu eksplicit typet `Omit<…Row, 'id'> & { id: '' }` (samme mønster som `initialRow`), med kort begrundende kommentar. Output-neutralt: literal-værdierne er uændrede og fortsat schema-gyldige (verificeret af både typecheck og ny round-trip-test). Tilføjet 3 nye `safeParse`-assertions i `eoRowInitialValues.test.ts`, der beviser at hver initial-række — givet et caller-sat id — parser rent mod sit schema (drift-værn, ikke kun per-felt-shape).

### 3. (Ingen — verificeret korrekt) Row-emptiness følger den kanoniske schema-drevne model
**Lokation:** `rowEmpty.ts`, `tableDraftRows.ts`.
`isSvieSmerteRowEmpty`/`isTafRowEmpty`/`isFerieRowEmpty`/`isOevrigeKravRowEmpty` udleder alle deres nøgler fra schemaerne via `nonIdKeysFromSchema(...)` og bruger `isEmptyByKeys` (al ikke-id-felter `=== undefined`) — præcis MEMORY-invarianten. Draft-lagets `isFraTilDraftRowEmpty` (UI: `fra`/`til` blanke efter trim) er bevidst adskilt og dokumenteret som ikke-fletbar med den persisterede schema-tomhed. Ingen handling.

### 4. (Ingen — verificeret korrekt) Row-id-håndtering: ingen RNG i setState-updatere
**Lokation:** `eoRowInitialValues.ts` (`generate*RowId`), `*TableModel.ts` (`ensure*Rows`), `sygedagpengeInsertRows.ts`, `midlertidigtEetInsertRows.ts`.
- `generate*RowId` (RNG via `createRowId`) bruges kun ved top-level `defaultTableData`-konstruktion og indsætnings-generatorer — **aldrig** inde i en React setState-updater. De updater-interne tom-række-id'er bruger `createEmptyRowId(prefix, seed)` (deterministisk) i consumer-tabellerne (StandardLoenTable/OffentligeYdelserTable/LoenudviklingManuelTable), jf. `project_table_row_id_persist_desync`.
- `ensure*Rows` (svie/taf/ferie/oevrige) bevarer eksisterende id'er (`row.id || createId()`) og tilføjer kun en trailing tom række — ingen RNG i en state-updater, ingen positionel id-grafting her.
- Indsætnings-generatorerne (`buildSygedagpengeRowsForRange`, `buildMidlertidigtEetAfgoerelseGroupsFromComputation`) genererer friske RNG-id'er, men resultaterne flettes via `insertOffentligeYdelserRowsBeforeTrailingEmpty` + `reconcileRowIdsByPosition` (uniqueness-guard, jf. `project_reconcile_rowid_dup`) i consumer-laget. De virtuelle `midlertidigt_eet`-rækker er rent transient compute-input (`eoSnapshot`), aldrig persisteret grid-state. Ingen handling.

### 5. (Ingen — verificeret korrekt) Crash-/inputrobusthed i parsing og afledte værdier
- `parseAarsloenRowInterval`: guarder tom/ugyldig måned/år (1–12, 1900–2100), uge (`fra.start > til.end`), dag (`fra > til`); returnerer `null` fail-closed. `hasAarsloenPeriodOrderError` returnerer korrekt `false` for `maaned` (ingen ordens-relation på én måned).
- `offentligeYdelserDerived.deriveOffentligeYdelserRow`: `ydelsePerDag = samletYdelse / antalDage` er beskyttet af `antalDage <= 0 → return …null` (ingen division med 0). `hasAnyAmount`-guard undgår at vise 0/dag for tomme beløb.
- `oevrigeKravAmountParser.parseOevrigeKravBeloeb`: negative/ikke-parsbare/over-/underflow-beløb → `null` (fail-closed via `toOre`/`ensureMoneyOre`-try/catch).
- `indtaegtPerioder`: `buildIncomeForRanges` afbryder fail-closed ved range-overlap (mod dobbelttælling), springer ikke-finite/≤0-bidrag, og kaster i DEV ved validation/parsing-mismatch. `parseAmount` (consumed) er undefined-/NaN-sikker (returnerer 0). `resolveIncomeBounds` returnerer `null` ved `boundsFra > boundsTil`.
- `sygedagpengeInsertRows`: `assertSygedagpengeRangeFullyCovered` fejler eksplicit (`SygedagpengeCoverageError`) ved manglende sats-/OP-dækning; `splitSygedagpengeRateSegments` springer `arbejdsdage ≤ 0`; `buildTillaegExpression` kaster ved tomt uge-resultat. `toExpressionAmount` kaster ved ikke-parsbart udtryk (fanger evt. NaN fra data-laget). Ingen handling.

### 6. (Ingen — verificeret korrekt) Initial values vs. schema-defaults — ingen dobbelt-sandhed
**Lokation:** `erstatningsopgoerelseInitialValues.ts`.
`createNewEOInitialValuesFromSettings` kører hele litteralen gennem `erstatningsopgoerelseSchema.parse({...})` (gruppe 3-mønstret), så initial values materialiseres gennem schemaet (form-contract §2.3). Den bevidste afvigelse — `kravPaaOevrigeErstatningskrav: 'Skjul'` for nye sager vs. schema-saneringsdefault `'Ja'` for legacy — er eksplicit dokumenteret i koden og må ikke "rettes tilbage". `createDefaultLoenindkomstAnsaettelsesforhold`/`createDefaultAngivetLoenLoenudvikling` bruger settings-afledte defaults via `resolveAppSettings`. Ingen handling.

### 7. (Ingen — verificeret korrekt) Form-kerneregel + arkitekturgrænser
- Ingen helper i scope kobler `onChange`-draft til beregning/visning; alle motor-/derived-funktioner tager committed `ErstatningsopgoerelseValues`/rækker. `loenindkomstStateCleanup` bevarer bevidst skjult committed input (kommenteret: gating sker i motor/validator, ikke ved skjult clearing — runtime-data-integritet §8.3).

Det er en ren præsentations-label-helper, ingen beregningslogik.
