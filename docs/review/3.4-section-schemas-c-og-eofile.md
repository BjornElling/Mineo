## Genbesøg 2026-06-04 (efter commits af 2026-06-03)

**Anledning:** Drift-dokumentet (`premis-drift-efter-2026-06-03.md`) markerede 3.4 som *Modsagt*: "Ingen fund der kræver rettelse" gjaldt en ældre EO-schema-tilstand. Fire commits landede bevidste breaking changes på `erstatningsopgoerelseSchemas.ts`/`enumSchemas.ts` (PERSISTED_DATA_VERSION 1.9 → 3.3).

**Verdikt:** Konklusionen *holder fortsat for `eoFileSchema.ts`* (to-spors save/load-modellen er uændret og korrekt), men "ingen fund der kræver rettelse" for EO-sektionsschemaet er nu **opdateret**: schemaet har bevidste breaking changes, som dog er korrekt håndteret pr. `schema-evolution.md` §3.1a.

**Verificeret korrekt mod nuværende kode (2026-06-04):**

1. **Felt-omdøbninger (breaking).** `beregnesSvieSmerteGodtgoerelse` → `kravPaaSvieSmerteGodtgoerelse` og `beregnesTabtArbejdsfortjeneste` → `kravPaaTabtArbejdsfortjeneste`, begge skiftet fra `jaNejEnum` til `jaNejSkjulEnum.default('Ja')`. Ingen migrator — bevidst tab af gammel værdi, jf. §3.1a (klassificeret som "bevidst breaking" i fingerprint-snapshottets kommentar). Verificeret via probe + ny regressionstest: de gamle feltnavne strippes som ukendte, sektionen parser, og de nye felter loades med default `'Ja'`.
2. **Nye felter.** `kravPaaOevrigeErstatningskrav` (`jaNejSkjulEnum.default('Ja')`) og `offentligeYdelserKommentarer` (`optionalString`). Begge med korrekt default/optional pr. Regel 1.1 — gamle filer uden felterne loader uden fejl.
3. **`afsluttesMedEnum` udvidet med `'Ingen'`.** `erstatningsopgoerelseAfsluttesMed: afsluttesMedEnum.default('Bekræftet godkendt')`. Tilføjelse af en enum-værdi er ikke-breaking ved load (gamle værdier 'Bekræftet godkendt'/'Underskrift-linje' er stadig gyldige). Default uændret.
4. **Fjernede regulerings-felter efterlader intet hul.** `allowReguleringMedOverenskomstDerIkkeDaekkerHelePerioden` og `allowReguleringMedUdloebMedMaaneder` er fjernet fra EO-schemaet og flyttet til device-lokale `appSettings` (`eoCaseReguleringSettings.ts` slettet, strip-laget i `appSettingsParse.ts` fjernet). Gamle filer med felterne strippes rent (verificeret i ny test). Ingen dangling reference i `erstatningsopgoerelseSchema`.

**Versionering korrekt:** 4 commits, 4 bumps (1.9→2.0, 2.0→3.1, 3.1→3.2, 3.2→3.3). Bumpet 2.0→3.1 bundter logisk 3.0 (omdøbninger) og 3.1 (nyt felt) i én commit — fingerprint-snapshottet narrerer begge som separate logiske trin. Sekvensen er monoton; hvert bump matcher en reel fingerprint-drift og er korrekt snapshot-opdateret.

## Tilfældighedsfund

- **`varigeMenSchema`** er minimal og korrekt: `mengrad` via `positiveWholePercentage('Méngrad')` (heltal 1–100), `beregningsdato` via `optionalIsoDateString`. Tests dækker decimal-afvisning, 0-afvisning og strict ukendt-felt. Ingen handling.
- **`eoFileSchema`** binder container-versionen til `FILE_FORMAT_VERSION` via `z.literal(...)` og har en præcis kommentar om at en ny top-level-feltstruktur kræver bevidst migrering (jf. `schema-evolution.md` Del 4A om `FILE_FORMAT_VERSION`-bump). Ejerskabet mellem `FILE_FORMAT_VERSION` (container) og `PERSISTED_DATA_VERSION` (sektioner) er korrekt afspejlet. Ingen handling.
- **Registry-kobling:** `eoFileDataInnerSchema` afleder alle sektions-keys fra `persistenceSchemas` (config/persistenceRegistry), så schema og registry ikke kan komme ud af sync. God single-source. Ingen handling.
- **`eoFileDataLoadSchema = z.preprocess(nullToUndefinedDeep, z.looseObject({}))`** — bevidst permissiv så load-pipelinen kan validere kendte sektioner enkeltvis og rapportere ukendte sektioner i preflight (jf. fail-soft-load-modellen i `persistence-contract.md`). Ingen handling.

## Konvergens

Konvergeret: renteberegning og varigeMen bruger udelukkende fundamentets combinatorer (3.1). `eoFileSchema` er den korrekte grænseflade mellem persistence-laget (gruppe 2) og schema-laget (gruppe 3) — den afleder sektioner fra registriet og håndhæver `schema-evolution.md`'s container/section-versionsskel.
